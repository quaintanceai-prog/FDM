# GPT-2 Joint Retrieval Reproduction

Reproduction of Table 4 (joint accuracy at N=32 extra channels) for GPT-2
Medium from the FDM paper.

## Paper claim

| Metric                | Value |
|-----------------------|-------|
| Action accuracy       | 98.3% |
| Joint accuracy @ N=32 | 88.2% |
| Independence estimate | 81.8% |

Claim: actual (88.2%) exceeds independence estimate (81.8%), implying
errors are positively correlated rather than independent.

## What was already on disk vs. what we produced

The other three models' joint accuracy JSONs were already checked into
the `ASK_FDM_CHECK/joint_retrieval/results/` directory and matched Table
4 to within 0.1%:

| Model   | Table 4 | JSON on disk |
|---------|---------|--------------|
| Qwen3   | 94.7%   | 94.67%       |
| LFM2.5  | 2.1%    | 2.07%        |
| Hermes3 | 99.9%   | 99.93%       |

GPT-2 had no JSON. This run produced `joint_accuracy_gpt2.json`.

## Test data and sample count

Each of the four models used its own stage-4 test JSONL, generated by
that model's encoder (different vocab, different seed-42 token map
bijection over that vocab). Samples are NOT shared across models —
each is a fresh 1,500-sample i.i.d. draw from the same schema.

For GPT-2, the on-disk test file (`fdm_40ch_turbo_v3_stage4_test.jsonl`,
dated Mar 18) was stale relative to the checkpoint (Apr 20). We
regenerated it with `random.seed(99999)` using the training script's
current encoder.

All four reproductions therefore measure the same population-level
statistic on different specific samples. At N=32, the 95% binomial CI
over 1500 samples at p=88% is approximately +/-1.6%, so a reproduction
number in the 86.6-89.8% range matches the paper claim.

## Changes needed to make the eval run on GPT-2

The checked-in `joint_accuracy_multi.py` runs out-of-the-box for Qwen3,
LFM2.5, and Hermes3 (all have >=32K position embeddings) but fails on
GPT-2 for two reasons.

### Change 1: Position embedding overflow

GPT-2 Medium has a 1024-token position embedding limit. Test samples
tokenize to ~1080-1100 tokens, exceeding this. `model.generate(
max_new_tokens=250)` would additionally try to extend position IDs
beyond the limit, triggering a CUDA device-side assert.

Paper's Table 2 footnote acknowledges this:
> "FDM signal expands to ~1080 tokens under GPT-2's tokenizer; final
> 56 tokens of encoder 2 truncated in every sample."

The checked-in eval does not implement this truncation.

**Fix applied**: a copy of the script at
`/workspace/joint_accuracy_multi_gpt2.py` adds a GPT-2-only branch
that:

- Tokenizes the `[MEMORY]...[/MEMORY]` block and the Question/Answer
  suffix separately
- Truncates the FDM block's tail if needed to fit within
  `MAX_POS - MAX_NEW - len(suffix)` tokens (1024 - 250 - 14 = 760 tokens)
- Passes the concatenated `fdm_head + suffix` tokens to generate

Non-GPT-2 models take the original code path unchanged.

### Change 2: Stale test data

The test JSONL on disk was dated Mar 18 while the checkpoint was dated
Apr 20. The encoder was modified between those dates (Table 5 footnote
mentions "Fixed normalization was introduced to support cross-length
transfer"). The Apr 20 model was trained on signals with the current
encoder config, so feeding it the older test data produced garbage
outputs with swapped channel values.

Concretely:
- Stale FDM text: 8,214 chars, 1,080 BPE tokens
- Fresh FDM text: 3,666 chars, 550 BPE tokens
- Size ratio 2.36x, structurally different (not a simple doubling)

**Fix applied**: `/workspace/regen_gpt2_stage4_test.py` regenerates
1,500 fresh samples by importing `TurboFDMSignalEncoder`, schemas,
templates, and `STAGES[4]` from the training script
`eidetic_real_fdm_e2e_40ch_turbo_v3.py`. Config:
- num_tokens_per_encoder = 256 (total signal: 512 tokens)
- a_high = 1.0, a_low = 0.25
- num_levels = 64, sample_rate = 100 Hz
- random.seed(99999) for reproducibility

Stale file preserved as `fdm_40ch_turbo_v3_stage4_test.jsonl.stale_mar18`.

## Note on MAX_NEW

An earlier version of the patch used `MAX_NEW=50` for GPT-2 to leave
more budget for FDM tokens. This was incorrect — the Context block in
a full Table 4 answer is ~200 tokens ("Decision: ABORT. Context:
TEAM=..., REGION=..., ..." with 32 channels). With MAX_NEW=50 only the
decision prefix and first 3-4 NAME=VALUE pairs fit in the output, so
per-channel scoring saw zero matches for ch13 onward even though the
model was generating correctly.

Final patch uses `MAX_NEW=250` for GPT-2 (same as other models).
With 550-token fresh FDM, total input + output = 564 + 250 = 814 tokens,
well under the 1024 position limit. No FDM truncation is actually
triggered on the fresh test data; the truncation code remains as a
safety net for any outlier samples.

## What truncation actually does: the signal structure

This section documents exactly what happens when the truncation branch
is invoked, why that specific truncation is semantically safe, and
whether it was triggered on this reproduction run.

### The FDM input structure (what's in the [MEMORY] block)

Each test sample's input has this structure:

    [MEMORY]<FDM tokens>[/MEMORY]\nQuestion: <text>\nAnswer:

The FDM block is produced by S-random interleaved dual encoding
(paper Section 2.2, "Turbo Dual Encoding"). Concretely:

    FDM block = [MEMORY] + encoder1_tokens + encoder2_tokens + [/MEMORY]

where:

- `encoder1_tokens`: 256 tokens from one natural-order pass of the
  signal encoder (amplitude samples quantized to 64 levels, mapped
  to vocabulary tokens via a seed-42 bijection).
- `encoder2_tokens`: 256 tokens from the SAME signal samples
  re-ordered via an S-random permutation (S=11, guaranteeing
  adjacent samples in encoder 1 are widely separated in encoder 2).

Encoder 2 carries **no new channel content** — it's a permuted
duplicate of encoder 1's signal. The S-random permutation gives the
model decorrelated views of the same 40-channel signal during
training, which improves gradient flow (paper's stated reason for
dual encoding).

After BPE tokenization of the fresh Apr-20 encoder output:
- Total FDM block: ~550 tokens
- Typical length breakdown: ~275 tokens encoder 1 + ~275 tokens
  encoder 2 (approximately, since BPE merges vary across random
  samples)

### What "truncate the tail" means here

The patched code does:

    fdm_ids = tokenizer.encode(fdm_part, add_special_tokens=False)
    suffix_ids = tokenizer.encode(suffix_part, add_special_tokens=False)
    budget = MAX_POS - MAX_NEW - len(suffix_ids)   # 1024 - 250 - 14 = 760
    if len(fdm_ids) > budget:
        fdm_ids = fdm_ids[:budget]

This cuts from the **end** of the FDM block. Since encoder 1 comes
first in the block, truncation attacks encoder 2's tail first. Only
after encoder 2 is fully cut would encoder 1 start getting truncated
— but that threshold is far beyond any input we'd realistically see.

Specifically, with 760 tokens of budget and ~275 tokens per encoder:

- 550-token input (fresh): no truncation at all. `fdm_ids[:760]`
  keeps everything.
- 1080-token input (stale Mar-18): 320 tokens of encoder 2 get cut.
  Encoder 1 remains intact (~275 tokens), encoder 2 keeps only its
  first ~185 tokens (out of ~530). Harsh.
- 900-token input (hypothetical middle case): 140 tokens of encoder 2
  get cut. Encoder 1 intact, encoder 2 keeps ~485 of ~625 tokens.

The paper's Table 2 footnote says "final 56 tokens of encoder 2
truncated in every sample" — implying paper used a 1024-budget with
a 56-token cut (i.e., they allowed ~968 FDM tokens). Our budget is
tighter because we reserve 250 tokens for generation, paper's eval
setup likely reserved less (or the paper's FDM block was shorter).
Without paper's exact eval script, we can't match budgets exactly,
but the semantic effect is the same: truncate encoder 2's tail,
preserve encoder 1 entirely.

### Why truncating encoder 2's tail is semantically safe

Three reasons:

1. **No unique signal content lost.** Encoder 2 is a permutation of
   encoder 1's samples, not new channel data. The model saw both
   encoders during training, so it can still decode the 40 channels
   from encoder 1 alone — just with less cross-attention-based
   redundancy to fall back on for error correction.

2. **Position-independent retrieval.** FDM's design claim (paper's
   central thesis) is that channel identity is fixed by carrier
   frequency at encoding time, not inferred from token position at
   runtime. Every token in either encoder carries all 40 channels'
   signal simultaneously in its amplitude value. Losing tokens from
   the end of encoder 2 doesn't localize the loss to any particular
   channel — it just reduces the sample count used for frequency
   decomposition from ~256 (encoder 2 full) to fewer.

3. **Paper's own eval used this truncation.** Paper reports 88.2%
   joint accuracy at N=32 for GPT-2. That number was produced with
   encoder 2 tail truncation applied. If truncation materially
   damaged retrieval, the paper's own numbers would reflect that.
   They don't (high-band per-channel accuracy stays at 92-99%), so
   empirically the redundancy loss is tolerable.

### What this reproduction run actually did

Critical point for interpreting our 93.7% result:

    Budget: 760 FDM tokens
    Actual fresh FDM length: ~550 tokens
    Truncation triggered: NEVER (0 of 1500 samples)

**On this reproduction run, the truncation code is dead code.** All
1500 samples fit within budget with room to spare, so each was
evaluated with the complete FDM signal — both encoders in full. The
truncation logic sits in the script as a safety net in case any
outlier sample tokenizes to more than 760 FDM tokens, but it never
activated.

This means our 93.7% joint accuracy at N=32 reflects **uncompromised
signal evaluation**, not a truncation-degraded one. There's no reason
to discount the 93.7% as "we lost some signal, maybe the real number
is lower" — we didn't lose any signal.

### Contrast with the stale Mar-18 data

If we had attempted to run the patched eval on the stale 1080-token
test data instead of regenerating fresh:

    Budget: 760 FDM tokens
    Stale FDM length: ~1080 tokens
    Truncation triggered: EVERY sample (1500 of 1500)
    Amount truncated: ~320 tokens (entire second half of encoder 2)

That would have been a 5.7x more aggressive truncation than paper's
56 tokens. It might still have worked — encoder 1 would survive —
but the result would not be directly comparable to paper's 88.2%
because the signal-redundancy degradation is qualitatively different.

Combined with the fact that the stale data's encoder config doesn't
match the Apr-20 model (amplitude normalization changed between
Mar 18 and Apr 20, as documented above), regenerating test data was
the correct call. Running on stale data with heavy truncation would
have produced a number that's uninterpretable — you couldn't tell if
any drift from 88.2% was due to (a) distribution mismatch, (b)
truncation severity, or (c) statistical variance.

### Summary table

| Scenario | FDM length | Budget (760) | Truncation triggered | Amount cut |
|----------|------------|--------------|----------------------|------------|
| Fresh data (our run) | ~550 | 760 | no | 0 tokens |
| Paper's original eval | ~968 (implied) | ~1000 (implied) | yes | 56 tokens |
| Stale Mar-18 data + our patch | ~1080 | 760 | yes | 320 tokens |

The "paper's original eval" row is inferred from the Table 2
footnote; the exact budget paper used isn't recoverable from this
repo, but the 56-token truncation figure is stated explicitly.

### Per-channel error distribution

Error analysis from the run:
- Total samples with errors: 95/1500
- Single-channel errors: 70 (74%)
- Multi-channel errors: 25 (26%)
- Pattern: **mostly independent** (paper said "correlated")

Top 5 error-prone channels:
- ch39 (COMMS, 40 Hz): 69 errors
- ch30 (FORMATION, 31 Hz): 8 errors
- ch31 (ARMOR, 32 Hz): 7 errors
- ch38 (DOCTRINE, 39 Hz): 5 errors
- ch15 (SUPPORT, 16 Hz): 4 errors

Single channel (ch39 COMMS at 40 Hz) accounts for **73% of errors**
(69/95) — confirming the paper's "errors concentrate at high carriers"
narrative even more strongly than paper's 64% (38/59) concentration.

### Interpretation

The reproduction **exceeds** the paper's claim (93.7% vs 88.2% joint
accuracy at N=32). Three likely reasons:

1. **Encoder evolution.** Table 5 footnote notes "Fixed normalization
   was introduced to support cross-length transfer" — the current
   encoder may have improved frequency resolution since the paper
   submission. Paper's 88.2% likely reflects an older checkpoint.

2. **Statistical variance** (unlikely). The 95% binomial CI at p=88.2%
   and n=1500 is approximately 86.6-89.8%; repro of 93.7% is outside
   this range, so sample variance alone doesn't explain it.

3. **Evaluator cleanup.** The checked-in eval script runs verbatim on
   Qwen3/LFM2.5/Hermes3 (which reproduced exactly). The GPT-2 run
   required no scoring change, only input-truncation and fresh test
   data — neither should affect accuracy.

### Qualitative claims hold

- Actual > independence (93.7% > 91.7%) ✓
- Errors concentrate at high carriers (ch39 = 73% of all errors) ✓
- Errors are NOT uniformly distributed across ch8-39 ✓

### Differences from paper narrative

- **"Errors are correlated" (paper)** vs **"mostly independent" (repro)**:
  paper's actual 88.2% vs independence 81.8% = +6.4 gap implied strong
  positive correlation. Our repro's +2.0 gap is much smaller, closer to
  actual independence. Consistent with the current model having fewer
  total errors, so the residuals behave more like independent noise.
  This is a difference in DEGREE of correlation, not direction.

## Clarifications on potentially confusing points

Future-me or any other reader will likely trip on these. Spelling them
out explicitly.

### "Two different encoders" — there are not

Confusion: The codebase contains both `TurboFDMSignalEncoder` (in
`eidetic_real_fdm_e2e_40ch_turbo_v3.py`, used for joint_retrieval /
Table 4) and `ScaledChannelEncoder` (in
`channel_density_scaling_multi.py`, used for channel_density / Table 3).
It is tempting to think these are two different encoder
implementations producing different signal representations.

Reality: They produce **byte-identical output** for the same memory
dict. Verified by direct test on Apr 23: given an identical 40-channel
memory dict and identical encoder parameters (num_tokens=256,
sample_rate=100 Hz, a_low=0.25, a_high=1.0, num_levels=64, seed=42),
both classes emit the same 3688-character string that BPE-tokenizes to
the same 554 tokens with the same starting sequence
('sovynaabiliaabiliaabiliasov Hayward silhouette...').

They are functionally one encoder maintained in two separate files for
each experiment's code convenience. The paper's methodology describes
one encoder; everything in Tables 3 and 4 uses the same signal
construction.

### The "stale Mar-18 data" is not a different encoder class — it's an
older version of the same encoder class

Confusion: The Mar-18 test data produces 1080-token FDM signals, while
the current Apr-20 encoder produces 550-token signals. 2.36x ratio.
One might assume these are different encoder classes.

Reality: The ratio change is a **code evolution** of the same
TurboFDMSignalEncoder class between Mar 18 and Apr 20. Some
combination of:

- Different amplitude normalization (sample-wise → fixed global)
- Different quantization bin-to-token mapping
- Different signal-to-string serialization

made the same conceptual encoder produce more BPE-efficient output.
Stale test data is incompatible with the current checkpoint not
because a different algorithm was used but because the **same
algorithm was revised**, and the trained model learned the current
revision's signal statistics.

The exact diff isn't recoverable from this pod (no git history of the
encoder file in our working directory), but the observation that
fresh-regenerated data today matches the current checkpoint's training
distribution confirms the current encoder is self-consistent.

### "Signal bandwidth" vs "statistical sample count"

Confusion: The encoder uses a 100 Hz sample rate. The eval uses 500
samples per config. These are both counts in seemingly similar units.

Reality: They measure **completely independent axes**.

- **100 Hz = sample_rate**: how many amplitude samples per second the
  encoder puts into one signal. Fixed by signal design. Each encoded
  memory produces 256 samples over 2.56 seconds at 100 Hz. Nyquist
  frequency = 50 Hz, so the 1-40 Hz carriers are representable.

- **500 = num_eval**: how many distinct random memory dicts the eval
  tests the model on. Each memory produces one signal (at 100 Hz);
  the eval averages scores across 500 such evaluations.

Sample rate is a signal-processing parameter. Num_eval is a
statistical-precision parameter. Bumping num_eval to 1500 doesn't
change the signal — it changes the confidence interval of the mean
accuracy estimate from +/-3-4% to +/-2%.

### Table 3 and Table 4 measure different things despite overlapping terminology

Confusion: Both "channel density" (Table 3) and "joint retrieval"
(Table 4) report accuracy metrics over FDM signals. Why do they need
separate experiments?

Reality:

- **Table 3 (channel density)** varies the **encoder configuration**:
  number of channels (40, 20, 10), carrier spacing (dense vs spread),
  and measures mean per-channel accuracy. The point is to probe how
  much total channel-packing the model can handle. One model is
  trained per config.

- **Table 4 (joint retrieval)** fixes the encoder at 40 channels with
  spread 1-40 Hz carriers and measures the **joint** accuracy — the
  probability that all N channels are simultaneously correct on the
  same sample. The point is to probe whether errors across channels
  are independent or correlated. All four architectures use the same
  encoder config.

They're orthogonal: Table 3 asks "how dense can we pack?"; Table 4
asks "given a fixed packing, how well does retrieval scale to
simultaneous multi-channel queries?"

### Table 3 GPT-2 row: the repo had NO density results for GPT-2

Confusion: The `results/` directories per model look asymmetric — Qwen3
has many, Hermes3 has 5, LFM2.5 has many, GPT-2 has only `lc_*` files.

Reality: The `lc_*.json` files under `results/gpt2/` are
**learning-curve ablations** (lc = learning curve), not density
scaling results. They measure how accuracy scales with training
sample count for single-encoding vs S-random comparison. They are
distinct from Table 3.

Table 3 density results (40ch, 20ch_dense, 20ch_spread, 10ch_dense,
10ch_spread) existed for Qwen3, Hermes3, and LFM2.5 but were never
produced for GPT-2. That's what our current Apr-22/23 training +
evaluation campaign produces.

### N=500 vs N=1500

Confusion: Our joint_retrieval eval used N=1500; density eval uses
N=500. Why not pick one?

Reality: Each eval script has its own default that matches the
original experimental setup the paper's table values came from. Using
N=500 here ensures the repro is apples-to-apples with paper Table 3.
Using N=1500 would give tighter CI but would no longer match the
paper's own methodology, potentially muddying "did we reproduce?" vs
"did we produce a better estimate?".

### The patched eval script vs the checked-in one

Confusion: We ran joint_retrieval with `/workspace/joint_accuracy_multi_gpt2.py`
(a patched copy), not `ASK_FDM_CHECK/joint_retrieval/joint_accuracy_multi.py`
(the checked-in one).

Reality: The patch is a GPT-2-only truncation branch. It adds
`if is_gpt2: truncate_fdm_to_fit()`, without changing any other
model's code path. Non-GPT-2 models would behave identically whether
run against the original or patched script.

The patched file is kept on pod at `/workspace/joint_accuracy_multi_gpt2.py`
rather than committed to the repo because (a) it specifically targets
GPT-2 and breaks symmetry with the other three models, (b) the
underlying issue — GPT-2's 1024 position limit being tight for
40-channel FDM — is architectural, not a bug in the shared script.
Committing a GPT-2-specific eval script to the shared location would
confuse future cloners. The correct long-term fix is either (a) a
config flag in the shared script that activates truncation per model,
or (b) a note in the README pointing to the patched file.

## Open questions for the paper

1. **Exact encoder change that broke Mar-18 data compatibility.** The
   2.36x size ratio and structural differences between stale and fresh
   FDM text point to a change in amplitude normalization or quantization
   levels sometime between Mar 18 and Apr 20. The exact commit isn't
   recoverable from this pod, but Table 5's footnote ("Fixed normalization
   was introduced to support cross-length transfer") suggests this is
   what happened for GPT-2 as well. Worth documenting in the paper's
   reproducibility section.

2. **Repo cloneability.** A fresh cloner of `ASK_FDM_CHECK` cannot reproduce
   Table 4 for GPT-2 because (a) the test data must be regenerated from
   the training script in `edeidic_memory_14_percent`, which is not in
   the public repo, and (b) the eval script needs the truncation patch.
   Either including a regeneration script in ASK_FDM_CHECK or pushing the
   test data to the paper1 datasets HF repo would close this gap.

3. **Do Qwen3/LFM2.5/Hermes3 test files have the same drift issue?**
   Their JSONs in the repo match Table 4 because they were produced when
   data and checkpoints were in sync. But reproduction from their checked-
   in test JSONLs against their current HF checkpoints may or may not
   work — worth checking if a future clone matters.

## Lessons for future experiments

- **Always timestamp-check training data against checkpoints** when
  debugging eval-time drift. A month gap is a red flag.
- **Plausible-looking but wrong outputs** (correct format, incorrect
  values) indicate distribution mismatch, not model failure.
- **Position-embedding-constrained models** like GPT-2 Medium need
  input-budget planning up front. Don't split the budget between input
  truncation and max_new_tokens without measuring how long the answer
  actually needs to be.
